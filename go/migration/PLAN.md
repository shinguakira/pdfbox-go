# Migration plan

Porting Apache PDFBox to Go: the capability slices, what each one needed, the
order they were taken in, and what *done* means for a slice and for a package.

The size of the Java tree, module by module, is in
[`mapping/modules.md`](mapping/modules.md); the per-package figures behind it
are in [`mapping/inventory.tsv`](mapping/inventory.tsv), regenerated by
[`scripts/inventory.ps1`](scripts/inventory.ps1).

`debugger`, `debugger-app`, `examples`, `benchmark`, `app` and `parent` are out
of scope — a Swing GUI, packaging shells, and documentation for the Java API.
Everything else is in scope, `tools` included.

**Every slice and every track in this plan is merged.** What each section below
records is what the slice was for and what it needed. Where a sentence reads
like a decision still to take, it names the branch that took it.
[`tasks/README.md`](tasks/README.md) is the branch index and carries each
branch's state.

## Strategy: vertical slices, not modules

**The module graph is a constraint, not a schedule.** It says what cannot be
skipped — no `fontbox` without `io`, no `pdfbox` without `fontbox`. It is a bad
unit of work:

- `pdfbox` alone is most of the port in one bucket — see
  [`mapping/modules.md`](mapping/modules.md) for how much. "Port the pdfbox
  module" is not a milestone anyone can act on or measure.
- Module order would mean finishing the whole of `fontbox` before opening a
  single PDF, when **opening a PDF needs no fonts at all**.

Porting by *package* has the same problem in smaller pieces: you can finish
twenty packages and still have nothing that runs end to end.

So the work is ordered by **capability slices**: pick something demonstrable,
port the minimum of every package it needs, leave the rest absent. Each slice
ends with something that runs on a real PDF.

This is also what the one successful PDFBox port did, cutting vertically across
what would be four Java modules rather than finishing a module before moving on.
The commit-by-commit evidence is in
[`conventions/prior-art.md`](conventions/prior-art.md).

### The scoreboard

`pdfbox/src/test/resources/input/` ships a text-extraction corpus with a
checked-in expected extraction and an expected reading-order-sorted extraction
beside each PDF. [`TESTDATA.md`](TESTDATA.md) counts it and says what else the
port is read against.

From slice 3 onward that corpus turned progress from a judgement into a number.
`TestTextStripper` walks it as a Go table test, and [`STATUS.md`](STATUS.md)
records the score each slice left it at.

## Slice 0 — byte plumbing (`pdfio`) — merged

The random access layer everything reads and writes through.

`RandomAccessRead` / `Write` / `RandomAccess`, `ReadBuffer`, `ReadWriteBuffer`,
`ReadView`, `SequenceRead`, `BufferedFile`, the `io.Reader`/`io.Writer`
adapters, `StreamCache`, and the ported Java tests.

The spill-to-disk path — `ScratchFile`, `ScratchFileBuffer`,
`MemoryUsageSetting`, the memory-mapped reader and the non-seekable stream
wrapper — was deferred out of this slice because it only matters for documents
too large for memory. `track/scratchfile` ported it; `STATUS.md`'s phase 0 row
is the record.

Note that `pdfbox-io` is **new in PDFBox 3.0** — the IO classes were extracted
from the core and moved to `java.nio`. This slice ported the newest architecture
in the codebase, not legacy.

**Runs when done:** nothing user-visible. This is the only slice without a demo.

## Slice 1 — open a document

`pdfbox-go info file.pdf` → version, page count, document information.

| Needs | From | Roughly |
| --- | --- | ---: |
| Object model | `pdfbox/cos` | 24 files |
| Lexer, xref tables, xref streams, object streams, trailer | `pdfbox/pdfparser` | 18 files |
| Flate only — enough to read xref and object streams | `pdfbox/filter` | 3 files |
| `PDDocument`, `PDPage`, `PDPageTree`, catalog, doc info | `pdfbox/pdmodel` | ~8 files |

No fonts. No content streams. No other filters.

`AGENTS.md` flags parsing and xref recovery as historically bug-prone — port
these line for line and bring the Java tests across verbatim. This is not the
place to improve on the original.

**The object model question, and how it was settled.** `COSBase` — an abstract
class plus a visitor over a mutable reference-identity graph — is the single
worst fit for Go in the whole codebase, and the package layout in
[`mapping/packages.tsv`](mapping/packages.tsv) mirrors the Java tree for a
reason the scope rule in [`BRANCHING.md`](BRANCHING.md) removed: there are no
upstream fixes to locate. The options and their trade-offs are in
[`conventions/prior-art.md`](conventions/prior-art.md).

`slice/1` kept the mirrored layout and split `COSBase` into an interface for the
contract and an embedded struct for the state, per
[`conventions/java-to-go.md`](conventions/java-to-go.md).
`go/pdfbox/cos/base.go` says so at the type, and everything above it inherited
that answer.

## Slice 2 — walk content streams

Dump the operator sequence of a page. No interpretation.

| Needs | From |
| --- | --- |
| Content stream lexer, `PDFStreamEngine`, operator dispatch | `pdfbox/contentstream` |
| Graphics state stack | `pdfbox/pdmodel/graphics/state` |
| `PDResources` | `pdfbox/pdmodel` |

Still no fonts — operators can be dumped without resolving what `Tf` refers to.

## Slice 3 — text extraction, simple fonts

**The corpus starts scoring here.**

| Needs | From |
| --- | --- |
| AFM metrics (Standard 14), TrueType basics | `fontbox/afm`, `fontbox/ttf` |
| `PDFont`, `PDSimpleFont`, Type1, TrueType, encodings | `pdfbox/pdmodel/font` |
| Text operators — `Tj`, `TJ`, `Tf`, `Td`, `Tm`, `T*` | `pdfbox/contentstream/operator/text` |
| `PDFTextStripper`, `TextPosition` | `pdfbox/text` |

`PDFTextStripper` is the most user-visible thing in PDFBox and its output
ordering has no specification to fall back on — only the ported tests and the
text-extraction corpus protect it.

## Slice 4 — text extraction, hard fonts

Drive the corpus score up.

CFF/Type2, Type1, CMap and CID handling from `fontbox`; `PDType0Font`,
`PDCIDFont` and the full encoding tables from `pdfbox/pdmodel/font`. This is the
bulk of `fontbox` — CFF and TrueType between them — and the point where font
substitution and embedded subsets start mattering.

## Slice 5 — encrypted documents

`pdfbox/pdmodel/encryption`, 19 files. Maps well onto `crypto/aes`, `crypto/rc4`
and `crypto/sha256`. `AGENTS.md` marks it sensitive; port the Java test vectors
with it. Independent of slices 3 and 4 — can run in parallel.

## Slice 6 — the rest of the filters, and images

LZW, ASCII85, ASCIIHex, RunLength, DCT, CCITT, JBIG2 from `pdfbox/filter`, and
`pdfbox/pdmodel/graphics/image`. `compress/zlib` and `image/jpeg` cover part;
CCITT and LZW need porting.

## Slice 7 — write and manipulate

`pdfbox/pdfwriter` (serialisation, incremental save) and `pdfbox/multipdf`
(merge, split). First slice that produces a PDF rather than consuming one.

## Slice 8 — forms, annotations, interactive features

`pdfbox/pdmodel/interactive/*` — AcroForms, annotations, actions, outlines,
signatures — and `pdfbox/pdmodel/interchange/*`. Large, but each subtree is
independent of the others and can be picked up separately.

## Slice 9 — rendering (merged, minus the raster)

The hard part. Java2D does the drawing in PDFBox: paths, clipping, compositing,
blend modes, soft masks, seven shading types, anti-aliasing. Go has no
equivalent. Three options:

- `golang.org/x/image/vector` plus hand-written compositing — small dependency,
  most work
- a Cairo or Skia binding — closest to Java2D, adds cgo
- port the geometry, defer the raster backend behind an interface

The third is the default. Two independent precedents support it: PdfBox-Android
vendored Harmony's `AffineTransform` and delegated rasterisation to
`android.graphics`; and PDFBox itself already does this pattern in-tree, where
`pdfbox-layout-awt` and `pdfbox-layout-fop` implement one glyph-layout interface
against two backends.

PdfPig shipped no renderer at all and still became the standard .NET choice for
reading PDFs. Cutting this slice permanently was a legitimate outcome.

**What happened: the third was taken, and the slice merged without the raster.**
Everything that computes is ported and runs — which paint applies, what the
stroke is made of, what the clip intersects to, which shading is evaluated
where. Only the last step sat behind `rendering.Backend` with nothing
implementing it, and `rendering.ErrNoBackend` was what every entry point that
would have had to make pixels answered.

**`track/raster` then wrote a backend**, in `go/pdfbox/rendering/raster`, over
`github.com/srwiley/rasterx` and `github.com/golang/freetype/raster`. The
`java.awt.Paint` and `PaintContext` classes of `graphics/shading`, and the
`rendering` classes that produce pixels, stay unported under their Java names
because their arithmetic went there instead; [`STATUS.md`](STATUS.md) says
which, and [`RASTER-PRECEDENT.md`](RASTER-PRECEDENT.md) is the comparison that
branch chose from.

## Parallel track — `xmpbox`

**No dependency on anything else in the build** — `pdfbox` hands back a raw
metadata stream and `xmpbox` parses it separately, as
[`mapping/modules.md`](mapping/modules.md) sets out. It could be ported at any
time by anyone, in parallel with every slice above, and it was the only part of
this project with no ordering constraint.

## Parallel track — `pdfbox-layout-*`

The glyph-layout backends. Only meaningful once slice 4 gave them fonts to
shape, and the in-tree precedent for the interface boundary slice 9 needed — see
[`mapping/modules.md`](mapping/modules.md). `track/pdfbox-layout` took them, and
what it built is not a port: PDFBox has no shaper of its own. `STATUS.md` has
that row.

## What is left

Every slice above is merged, and so is every track. **One Java class this plan
counts in scope is not in the port:** `tools/PrintPDF`, which waits on a
printing system — `java.awt.print.PrinterJob` and `javax.print` have no Go
equivalent, and no pure-Go library supplies one. `go/tools/notbuilt.go` is the
list and the reason, and `STATUS.md` carries the row.

Four things this plan counted in scope and no slice claimed — the raster
backend, `multipdf`, the `tools` commands waiting on those two, and the
deferrals whose reason had stopped being true — were grouped into four branches:
`track/raster`, `track/multipdf`, `track/imageio` and `track/stale-deferrals`.
All four are merged. A fifth followed them that is not a port at all; see "After
the port" below. The order came from what the missing commands import; the
**contents** came from an audit, because the 891-class survey this plan leaned
on missed `multipdf` outright. [`BRANCHING.md`](BRANCHING.md) carries the
grouping and the critical path, [`STATUS.md`](STATUS.md) carries the audit and
the commands to re-run it, and `tasks/` carries one file per branch.

**A deferral is not a record of what is missing; it is a record of what was
missing on the day it was written.** Nothing in this plan went back to check
when the thing a deferral named was ported, and four deferrals had come to name
a dependency that was already in the tree. `track/stale-deferrals` re-checked
every one of them.

## After the port: the Java's bugs

Everything above is a port, and a port reproduces what it ports. Where the Java
is wrong, the Go was wrong the same way on purpose: the reference is the Java,
a silently corrected bug makes the two behave differently, and "the Java does
this too" is the answer that made every strange behaviour cheap to investigate
for the length of this migration. Each one is recorded in
[`JAVA-BUGS.md`](JAVA-BUGS.md), with where the Go carries it.

**That rule expires when the port does.** Nothing downstream benefits from a
reproduced defect once there is nothing left to port.

So there is a fifth branch, and it is the only one in this plan that is not a
port: **`track/java-bug-fixes`**. It went through `JAVA-BUGS.md` entry by entry
and fixed in the Go the ones worth fixing. What it may and may not do — it
changes no Java, it deletes no entry, it goes last, and it triages every entry
in writing first — is in [`BRANCHING.md`](BRANCHING.md) and in its task file,
[`tasks/track-java-bug-fixes.md`](tasks/track-java-bug-fixes.md). Every entry in
`JAVA-BUGS.md` now says which it is, fixed in the Go or kept and why, and that
file carries the counts.

## How the work is done: test first, always

**Every package is ported test-first — the Java test is ported before the Go
implementation exists**, and assertion values are copied verbatim from the Java,
never recomputed. [`conventions/tdd.md`](conventions/tdd.md) is the rule, and
why porting makes it stronger than ordinary TDD hygiene. It is the rule this
entire plan runs on, not a preference.

## Definition of done, per unit of work

A slice is done when it runs end to end on a real PDF and its corpus score is
recorded. A package is done when it builds, `go vet` is clean, the ported Java
tests pass, its row in [`STATUS.md`](STATUS.md) is updated, and every deliberate
deviation from Java carries a comment saying why.

A package with implementation and no ported tests is **not** partially done. It
is unverified, and `STATUS.md` records it that way.

Partial packages are expected and normal under this plan — that is the cost of
slicing vertically. `STATUS.md` tracks what is actually ported per package so
the partial state stays visible rather than being mistaken for finished.
